01

Why Schema Refinement?

When we group too many attributes into one relation, we create redundancy, which leads to anomalies.

Bad design — LECTURER table
LECTURER(id, name, address, salary, deptno, dname, building)

If the building changes for a department, we must update every lecturer row in that dept → Update Anomaly
Deleting the last lecturer removes department info → Deletion Anomaly
Can't add a dept with no lecturers → Insertion Anomaly

Solution

Decompose into smaller relations using Normalization — a formal process based on Functional Dependencies.

Two critical decomposition properties

Lossless-Join
When we join the decomposed relations back, we get exactly the original relation — no spurious (fake) tuples. Required: the common attributes must be a key in at least one of the decomposed relations.
Dependency Preservation
Every FD in the original relation can still be checked by looking at one of the decomposed relations — no need to join first. Always achievable for 3NF, not always for BCNF.
02

Functional Dependencies (FDs)

Definition
X → Y means: if two tuples agree on X, they must agree on Y. X functionally determines Y.

If SSN → ENAME, then no two rows can have the same SSN but different ENAME.

EMP_DEPT example — understanding FDs
SSNENAMEBDATEADDRDNUMDNAMEDMGR
101Alice1990ColomboD1ITBob
102Carol1988KandyD1ITBob
103Dave1995GalleD2HREve
SSN → {ENAME, BDATE, ADDR, DNUM} // SSN determines employee info
DNUM → {DNAME, DMGR} // DNUM determines dept info — causes redundancy!

03

Armstrong's Axioms

These 3 rules let you infer all implied FDs. They are sound (produce only valid FDs) and complete (can derive all valid FDs).

Reflexivity
If Y ⊆ X, then X → Y
An attribute always determines itself or a subset. e.g. {A,B} → A
Augmentation
X→Y implies XZ→YZ
Adding same attrs to both sides keeps FD valid. e.g. A→B means AC→BC
Transitivity
X→Y & Y→Z implies X→Z
Chain FDs together. e.g. SSN→DNUM, DNUM→DNAME → SSN→DNAME

Additional derived rules (from the axioms)

RuleStatementExample
UnionX→Y and X→Z implies X→YZSSN→ENAME, SSN→BDATE → SSN→{ENAME,BDATE}
DecompositionX→YZ implies X→Y and X→ZSSN→{ENAME,BDATE} → SSN→ENAME and SSN→BDATE
Memory trick — RAT
Reflexivity · Augmentation · Transitivity
"A RAT infers all FDs"
04

Attribute Closure (X⁺)

Definition
X⁺ is the set of all attributes that X can functionally determine (using the given FDs). If X⁺ contains all attributes → X is a superkey.

Algorithm to compute X⁺

1
Start
Set closure = X (just the starting attributes)
2
Repeat
For every FD U→V in F: if U ⊆ closure, then add V to closure
3
Stop
When no more attributes can be added. The closure is X⁺.
Worked example — EMP_DEPT

F = { SSN → {ENAME, BDATE, ADDR, DNUM}, DNUM → {DNAME, DMGR} }

Compute {SSN}⁺:

Start: closure = {SSN}
Apply SSN→{ENAME,BDATE,ADDR,DNUM}: closure = {SSN, ENAME, BDATE, ADDR, DNUM}
Apply DNUM→{DNAME,DMGR}: closure = {SSN, ENAME, BDATE, ADDR, DNUM, DNAME, DMGR}
{SSN}⁺ = {SSN, ENAME, BDATE, ADDR, DNUM, DNAME, DMGR} → SSN is the key!

Compute {DNUM}⁺:

Start: closure = {DNUM}
Apply DNUM→{DNAME,DMGR}: closure = {DNUM, DNAME, DMGR}
{DNUM}⁺ = {DNUM, DNAME, DMGR} → DNUM is NOT a key (doesn't cover all attrs)
Exam tip — finding candidate keys
To find ALL candidate keys: try each attribute (and combinations) using attribute closure. If X⁺ = all attributes, X is a superkey. If no proper subset of X is also a superkey, then X is a candidate key. Start with single attributes, then pairs.
05

Normal Forms — 1NF to BCNF

Normal forms are levels of "goodness" of a schema. Higher = less redundancy.

1NF
All attribute domains must be atomic (indivisible)
No multi-valued attributes, no repeating groups. Every cell holds a single value.
FAIL: phone = {0771234, 0112345} → PASS: separate rows per phone
2NF
1NF + No partial dependency on any candidate key
Every non-prime attribute must depend on the whole key, not just part of it. Only relevant when key is composite.
EMP_PROJ(NIC, PNUM, HOURS, ENAME, PNAME) — ENAME depends only on NIC (partial!)
3NF
2NF + No transitive dependency on any key
No non-prime attribute depends on another non-prime attribute. SSN→DNUM→DNAME is a transitive dependency — remove it.
EMP_DEPT → decompose into EMP(SSN,ENAME,BDATE,ADDR,DNUM) + DEPT(DNUM,DNAME,DMGR)
BCNF
For every nontrivial FD X→A, X must be a superkey
Stricter than 3NF. If any determinant is not a superkey, decompose. May lose dependency preservation.
CSZ: CS→Z (CS is key ✓), Z→C (Z is NOT a superkey ✗) → violates BCNF
1NF test
Are all values atomic? No lists, no sets?
Fix: split multi-values into rows
2NF test
Does every non-prime attr need the full composite key?
Fix: split partial deps into new table
3NF test
Does any non-prime attr depend on another non-prime?
Fix: move transitive deps to new table
BCNF test
For every X→Y (non-trivial), is X a superkey?
Fix: decompose into R-Y and XY
Full normalization walkthrough — EMP_DEPT

Starting relation:

EMP_DEPT(SSN, ENAME, BDATE, ADDR, DNUM, DNAME, DMGR)
F = { SSN → {ENAME, BDATE, ADDR, DNUM}, DNUM → {DNAME, DMGR} }

1NF check: ✓ All values are atomic

2NF check: Key = SSN (single attr) → No partial dependency possible ✓

3NF check: SSN → DNUM → DNAME is TRANSITIVE ✗ → Decompose!

ED1: EMP(SSN, ENAME, BDATE, ADDR, DNUM)
ED2: DEPT(DNUM, DNAME, DMGR)

BCNF check on ED1: SSN→{ENAME,BDATE,ADDR,DNUM} — SSN is the key ✓

BCNF check on ED2: DNUM→{DNAME,DMGR} — DNUM is the key ✓

Both ED1 and ED2 are in BCNF!

BCNF vs 3NF — key difference for exam

3NF is always dependency-preserving. BCNF may NOT be dependency-preserving. If asked why BCNF can fail dependency preservation, use example: R(C,S,Z), CS→Z, Z→C — decomposing loses CS→Z.

Lossless-join test

Decomposition of R into X and Y is lossless if: the attributes common to X and Y form a key in X or in Y. If this holds → no spurious tuples when joining back.

07

Minimal Cover Algorithm

Definition
A minimal cover G for F is an equivalent set of FDs where: (1) closure of G = closure of F, (2) every RHS has a single attribute, (3) no FD or LHS attribute can be removed while preserving the closure.

3-step algorithm

1
Split RHS — put every FD in standard form
Each FD must have exactly ONE attribute on the right side.
e.g. A→BC becomes A→B and A→C
2
Minimize LHS — remove redundant attributes from LHS
For each FD AB→C, check if A→C already holds (i.e. if C ∈ {A}⁺). If yes, remove B from LHS.
3
Remove redundant FDs
For each FD X→A, check if A ∈ X⁺ using the remaining FDs (excluding this one). If yes, this FD is redundant — remove it.
Worked example — finding minimal cover

F = { SSN → {ENAME, BDATE, ADDR, DNUM}, DNUM → {DNAME, DMGR} }

Step 1 — Split RHS:

SSN → ENAME, SSN → BDATE, SSN → ADDR, SSN → DNUM, DNUM → DNAME, DNUM → DMGR

Step 2 — Minimize LHS: all LHS are single attributes → no change

Step 3 — Remove redundant FDs:

Check SSN→ENAME: is ENAME ∈ {SSN}⁺ without this FD? Only from DNUM→... No. Keep it.
// Repeat for each FD — none are redundant here
Minimal cover G = { SSN→ENAME, SSN→BDATE, SSN→ADDR, SSN→DNUM, DNUM→DNAME, DNUM→DMGR }
08

FD Equivalence

Two sets F and G are equivalent if F⁺ = G⁺. To prove this, show both directions:

1
Prove F is covered by G
For every FD X→Y in F, compute X⁺ using only G. Check that Y ⊆ X⁺.
2
Prove G is covered by F
For every FD X→Y in G, compute X⁺ using only F. Check that Y ⊆ X⁺.
Worked example — 2018 past paper style
F = {A→C, AC→D, E→AD, E→H}
G = {A→CD, E→AH}

Prove G covered by F (compute using F):

{A}⁺ w.r.t. F = {A, C, D} → covers A→CD in G ✓
{E}⁺ w.r.t. F = {E, A, D, H, C} → covers E→AH in G ✓

Prove F covered by G (compute using G):

{A}⁺ w.r.t. G = {A, C, D} → covers A→C in F ✓
{A,C}⁺ w.r.t. G = {A, C, D} → covers AC→D in F ✓
{E}⁺ w.r.t. G = {E, A, H, C, D} → covers E→AD and E→H in F ✓
F and G are equivalent! ✓

Worked Past Paper Example (2023)

R(StudentID, CourseID, Instructor, Room, Time) with FDs:

StudentID, CourseID → Instructor
Instructor → Room, Time
CourseID → Room

a) Find candidate keys

Attribute closure computation
Try {StudentID, CourseID}⁺:
Start: {StudentID, CourseID}
Apply SID,CID→Instructor: {StudentID, CourseID, Instructor}
Apply Instructor→Room,Time: {StudentID, CourseID, Instructor, Room, Time}
{StudentID, CourseID}⁺ = ALL attributes → Candidate Key!
No single attribute gives all attrs → {StudentID, CourseID} is the only candidate key.

b) Convert to BCNF

BCNF decomposition

Check each FD — is the LHS a superkey?

SID,CID → Instructor: {SID,CID} is a superkey ✓ OK
Instructor → Room,Time: Instructor is NOT a superkey ✗ // BCNF violation!
CourseID → Room: CourseID is NOT a superkey ✗ // BCNF violation!

Decompose for Instructor→Room,Time:

R1: INSTRUCTOR_INFO(Instructor, Room, Time)
R2: ENROLLMENT(StudentID, CourseID, Instructor)

Check R2 — only FD is {SID,CID}→Instructor, {SID,CID} is key ✓ BCNF!

Note: CourseID→Room is now lost (not preserved in any single relation) — BCNF is not dep-preserving here.

c) Minimal FD set

Finding minimal cover for S(A,B,C,D)
Given: A→BC, B→C, A→B, AB→D, D→A

Step 1 — Split RHS:

A→B, A→C, B→C, A→B, AB→D, D→A
Remove duplicate A→B: A→B, A→C, B→C, AB→D, D→A

Step 2 — Minimize LHS of AB→D:

Is D ∈ {A}⁺? {A}⁺ = {A,B,C} — D not included → B is needed
Is D ∈ {B}⁺? {B}⁺ = {B,C} — D not included → A is needed → AB→D stays

Step 3 — Remove redundant FDs:

Check A→C: is C ∈ {A}⁺ without A→C? {A}⁺ = {A,B,C} (via A→B, B→C) ✓ → A→C is redundant! Remove.
Minimal cover = { A→B, B→C, AB→D, D→A }

Quick Cheat Sheet

Schema Refinement — exam-ready reference

1NF
All values atomic (no lists/sets)
2NF
1NF + no partial dependency on any candidate key
(only matters with composite keys)
3NF
2NF + no transitive dependency
(nonprime attr must not depend on another nonprime)
BCNF
For every nontrivial X→A, X must be a superkey
(BCNF ⊂ 3NF — stricter; may lose dep-preservation)
X⁺ algo
closure=X; while change: if U⊆closure add V for each U→V
Min cover
1) Split RHS → single attr
2) Minimize LHS
3) Remove redundant FDs
Equivalence
Show F covered by G AND G covered by F (use X⁺ both ways)
Lossless
R1 ∩ R2 must be a key of R1 or R2
Dep-pres
Every FD in F can be checked in one relation (no join needed)
3NF: always possible · BCNF: not always
Memory trick — normal form order
"Atomic values → No partial → No transitive → Superkey only"
1NF → 2NF → 3NF → BCNF

Each step builds on the previous. BCNF is the strictest but trades away dependency preservation.
Marks breakdown — what to write in Q1
3NF conversion (2–4 marks): Identify transitive deps, decompose, show resulting relations clearly.

Attribute closure (4 marks): Show every step of the algorithm — don't skip! Write closure = {} at each iteration.

Dependency preservation (4 marks): Define it, then show an example of BCNF failing (e.g. R(C,S,Z), CS→Z, Z→C).

Minimal cover (7–10 marks): Do all 3 steps explicitly. Prove equivalence by computing X⁺ both ways.
